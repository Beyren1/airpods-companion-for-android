# Как выпустить версию

Выпуск — это APK, подписанный вашим личным ключом, на странице Releases репозитория.
Ключ делается один раз, дальше каждый выпуск — это два нажатия в GitHub.

## Почему ключ так важен

Android ставит обновление поверх приложения, только если оно подписано **тем же** ключом.
Если ключ потерять, выпустить обновление будет невозможно: всем придётся удалять приложение
и ставить заново, со сбросом настроек. Поэтому:

- сохраните файл ключа и пароль в двух местах (например, менеджер паролей и флешка);
- никогда не кладите ключ и пароль в репозиторий и не отправляйте их в чаты.

## Шаг 1. Создать ключ (один раз)

Нужна программа `keytool`, она входит в Java. Проще всего:

- **Windows.** Если стоит Android Studio, `keytool` уже есть:
  `"C:\Program Files\Android\Android Studio\jbr\bin\keytool.exe"`.
  Иначе установите Java с <https://adoptium.net> (Temurin 17 или новее, установщик .msi,
  галочка «Set JAVA_HOME»), после этого `keytool` работает в любой командной строке.
- **macOS / Linux.** Установите Temurin с <https://adoptium.net> или через `brew install temurin`.

Откройте терминал (Windows: «PowerShell») в папке, где будет лежать ключ, и выполните одну строку:

```
keytool -genkeypair -v -keystore pods-release.jks -alias pods -keyalg RSA -keysize 4096 -validity 10000 -storetype PKCS12
```

Программа спросит:

1. **Пароль** (дважды). Придумайте длинный, символы при вводе не видны — это нормально.
2. Имя, организацию, город и т. д. Можно ввести своё имя и пропустить остальное клавишей Enter.
   Эти данные видны любому, кто посмотрит подпись APK.
3. «Is ... correct?» — введите `yes`.

Появится файл `pods-release.jks`. Это и есть ключ. Имя ключа (alias) — `pods`.

## Шаг 2. Превратить ключ в текст

GitHub хранит секреты только как текст, поэтому файл кодируется в base64.

- **Windows (PowerShell), в той же папке:**
  ```
  [Convert]::ToBase64String([IO.File]::ReadAllBytes("$PWD\pods-release.jks")) | Set-Content -NoNewline pods-release.txt
  ```
- **macOS:** `base64 -i pods-release.jks -o pods-release.txt`
- **Linux:** `base64 -w0 pods-release.jks > pods-release.txt`

Откройте `pods-release.txt` в Блокноте — там одна длинная строка из букв и цифр.

## Шаг 3. Добавить секреты в GitHub

На странице репозитория: **Settings → Secrets and variables → Actions → New repository secret**.
Создайте четыре секрета (имя — ровно как в таблице):

| Name | Secret |
|---|---|
| `RELEASE_KEYSTORE_BASE64` | всё содержимое `pods-release.txt` |
| `RELEASE_KEYSTORE_PASSWORD` | пароль из шага 1 |
| `RELEASE_KEY_ALIAS` | `pods` |
| `RELEASE_KEY_PASSWORD` | тот же пароль из шага 1 (в формате PKCS12 он у ключа и хранилища общий) |

После этого `pods-release.txt` можно удалить, а `pods-release.jks` убрать в надёжное место.
Секреты после сохранения не видны даже вам; их видит только сборка.

## Шаг 4. Собрать выпуск

1. Убедитесь, что всё нужное влито в `main`.
2. Вкладка **Actions** → слева **Release** → справа **Run workflow** → ветка `main`,
   галочка **Create draft release** включена → зелёная кнопка **Run workflow**.
3. Через несколько минут запуск станет зелёным. Если красный — откройте его, текст ошибки
   скажет, какого секрета не хватает или что не так.
4. Вкладка **Releases** (справа на главной странице репозитория) → черновик
   **Pods Companion 1.0.0** с файлом `PodsCompanion-1.0.0.apk`. Его видите только вы.
5. Скачайте APK из черновика, поставьте на телефон и проверьте.
6. Если всё хорошо — **Edit** (значок карандаша) → **Publish release**. С этого момента выпуск
   виден всем, а в репозитории появляется тег `v1.0.0`.

## Перед установкой на свой телефон

Выпуск — это отдельное приложение от тех сборок, что вы ставили для проверки (`app-debug`,
`app-fast`): у них разные идентификаторы, поэтому настройки не переносятся. **Удалите
проверочную сборку**, иначе две копии будут одновременно подключаться к наушникам и мешать
друг другу.

## Следующие версии

1. В `app/build.gradle.kts` увеличьте `versionCode` на 1 (было 1 — станет 2) и поменяйте
   `versionName` (например, `1.0.1` для исправлений, `1.1.0` для новых функций).
2. По желанию добавьте описание в `docs/release-notes/v<версия>.md`, иначе GitHub составит
   его из списка PR.
3. После вливания в `main` — шаг 4.

## А Google Play?

Можно, но это отдельная работа:

- аккаунт разработчика Google Play: разовый взнос 25 $ и проверка личности;
- для новых личных аккаунтов — закрытое тестирование минимум с 12 тестировщиками 14 дней
  перед публикацией;
- Play принимает AAB, а не APK (сборка `bundleRelease`, добавить в CI просто);
- анкеты о данных и разрешениях. Заметные вопросы будут к доступу к уведомлениям, ответу
  на звонки и окну поверх других приложений: каждое нужно объяснить, иначе приложение отклонят;
- приложение использует скрытые функции Android для прямой связи с наушниками (через
  библиотеку HiddenApiBypass). Play это формально не запрещает, но это риск при проверке;
- название и картинки не должны выглядеть как продукт Apple.

Если захотите, подготовлю всё это отдельно.
