# Pods Companion for Android: план и оценка реализуемости

Этап 1 из «Формата работы». Рабочее название: **Pods Companion** (без товарных знаков Apple в названии и иконке).

## 1. Два уровня работы приложения

| Режим | Канал | Что даёт | Требования |
|---|---|---|---|
| **Базовый (без root)** | BLE advertising Apple (company ID `0x004C`, тип `0x07` Proximity Pairing) | Модель, цвет, заряд L/R/кейс (шаг 10%), зарядка, крышка, «в ухе», какой наушник основной | Android 10+, BLUETOOTH_SCAN |
| **Расширенный (AAP)** | Bluetooth Classic L2CAP, PSM `0x1001` (Apple Accessory Protocol) | Шумоподавление, Conversational Awareness, Adaptive, жесты, переименование, микрофон, точный заряд (1%), точное ухо, данные головы | Работающий L2CAP BR/EDR к PSM 0x1001: на большинстве прошивок нужен root + Xposed/патч стека; на части прошивок (по сообщениям, ColorOS/OxygenOS новых версий) работает без root. Проверим на вашем телефоне |

Почему AAP не работает «из коробки»: публичный API Android даёт L2CAP-сокеты только для BLE (`createL2capChannel`, LE CoC). Классический L2CAP открывается через скрытый API (`BluetoothSocket` с `TYPE_L2CAP` / `createL2capSocket`), который ограничен hidden-API политикой, а в стоковом стеке (Fluoride/Gabeldorsche) есть особенность, из-за которой AirPods рвут соединение. LibrePods решает это хуком `libbluetooth` через Xposed (root). Поэтому архитектура строится так: **всё, что можно, работает в базовом режиме, а AAP подключается как опциональный транспорт**.

### Что невозможно или возможно частично (честно)

| Функция | Статус |
|---|---|
| Siri | Нет. Долгое нажатие можно повесить на Google Assistant |
| Автопереключение между устройствами Apple | Нет (работает через iCloud) |
| Find My / локатор | Нет. Можно показывать «последнее место, где наушники были на связи» по GPS телефона |
| Пространственное аудио с отслеживанием головы | Нет как системная функция. Сырые данные сенсоров по AAP получить можно, но встроить их в аудиотракт Android нельзя |
| Слуховой аппарат, Hearing Test, Hearing Protection | Нет (требует калибровки и сертифицированного профиля Apple) |
| Обновление прошивки наушников | Нет |
| Качество звука AAC как на iPhone | Частично: зависит от кодеков телефона |

## 3. Архитектура (кратко, детали на этапе 2)

Модули: `:app`, `:core-bluetooth` (BLE scan, L2CAP-транспорт, переподключение), `:protocol-aap` (чистый Kotlin, без Android: парсинг/сборка пакетов, state machine, тесты), `:data` (репозитории, DataStore), `:ui` (Compose + M3, виджет, тайл).

Слой AAP:
- `AapTransport` (интерфейс): `NoopTransport` в базовом режиме, `L2capReflectionTransport` для прошивок без ограничений, позже вариант для Xposed-модуля.
- `AapCodec`: кадры вида `04 00 04 00 <opcode LE16> <payload>`; handshake → включение функций → подписка на уведомления → события (батарея, ухо, режим шумоподавления, настройки).
- `AapSession` (state machine): Disconnected → Connecting → Handshaking → Ready → (Reconnecting с экспоненциальной задержкой).
- Источник данных о наушниках объединяет advertising и AAP, при наличии AAP приоритет у него.

Форматы пакетов берём из публичного реверса (LibrePods (GPL-3.0), CAPod (GPL-3.0), OpenPods (GPL-3.0)) только как справочник и сверяем с вашими дампами. Код пишем с нуля. Если когда-нибудь захотите взять их код напрямую, проект придётся выпускать под GPL-3.0, это решим отдельно.

Батарея: скан `SCAN_MODE_LOW_POWER` с фильтром по manufacturer ID `0x004C`, переход в `LOW_LATENCY` на несколько секунд при открытии кейса или старте приложения, остановка, если AirPods не видны N минут и не подключены по A2DP; повторный старт по событию подключения A2DP.

## 4. Этапы

1. Парсер advertising + экран заряда (без root, работает у всех).
2. Foreground Service, уведомление с зарядом, автопауза по уху.
3. AAP-клиент: транспорт, handshake, state machine, hex-лог, тесты.
4. Шумоподавление, CA, жесты, переименование, микрофон, жесты головой.
5. Виджет и Quick Settings Tile.

После каждого этапа дам инструкцию проверки на устройстве.

## 5. Какие дампы понадобятся и как их снять

### A. Advertising (нужно для этапа 1, root не нужен)

Цель: реальные пакеты вашей модели для unit-тестов и сверки model ID и цвета.

1. Установите **nRF Connect for Mobile** (Nordic).
2. Включите сканирование, найдите устройство с Manufacturer data `0x004C`, где данные начинаются с `07 19`.
3. Снимите raw-данные (кнопка RAW или «Clone») в состояниях:
   - кейс открыт, оба наушника в кейсе, кейс на зарядке и без;
   - один наушник вынут; оба вынуты;
   - оба в ушах; один в ухе;
   - крышка закрыта (если пакет ещё виден).
4. Пришлите hex-строки и подпишите состояние и примерный заряд, который показывает iPhone или система.

### Б. HCI snoop log (нужно для этапа 3–4)

1. «Настройки → Для разработчиков → Журнал отслеживания Bluetooth HCI» (Enable Bluetooth HCI snoop log) → «Включено».
2. Выключите и включите Bluetooth.
3. Воспроизведите сценарий (подключение наушников, вынимание из уха, переключение режима кнопкой на наушнике).
4. `adb bugreport bugreport.zip` → внутри `FS/data/misc/bluetooth/logs/btsnoop_hci.log` (путь зависит от прошивки; с root можно взять напрямую).
5. Откройте в **Wireshark**, фильтр `btl2cap.psm == 0x1001` или `btl2cap`.

Без root на Android этот лог покажет AAP только если наше приложение сможет подключиться по PSM 0x1001. Поэтому самый ценный источник ниже.

### В. Дамп с устройства Apple (очень желательно для этапа 4, если есть доступ)

Если есть Mac или iPhone (даже чужой на время): на macOS это **PacketLogger** из Additional Tools for Xcode, на iOS это профиль Bluetooth logging от Apple + sysdiagnose. Снимите переключение всех режимов шумоподавления, CA, Adaptive, смену жестов, переименование, выбор микрофона. Это даст точные ID команд именно для вашей прошивки.
